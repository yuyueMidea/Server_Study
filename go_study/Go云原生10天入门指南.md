# Go 云原生 10 天快速入门指南

> 适合人群：会写基础 Go 代码、能实现单体服务的新手，目标是在 10 天内建立起"容器化 → 编排 → 可观测 → 自动化部署"的完整云原生知识框架，并亲手跑通一个真实可部署的项目。
>
> 使用方式：每天投入 1.5～3 小时，包含"学习内容 + 动手练习 + 检查点"。不要只看不做——云原生是一门手感科目，命令敲得越多，理解得越快。

## Day 1：Go 并发与工程规范强化

云原生服务本质是"高并发地处理网络请求"，Go 的并发原语是整个学习路径的地基，必须先打牢。

**学习内容**
- goroutine 与 channel 的基本用法，重点理解"不要通过共享内存来通信，而要通过通信来共享内存"
- `sync.WaitGroup`、`sync.Mutex` 的使用场景，以及为什么在云原生服务里更推荐 channel 而不是锁
- `context.Context`：超时控制、取消传播、跨 goroutine 传值——这是云原生 Go 服务里几乎每个函数签名都会出现的类型
- Go modules（`go mod init`、`go mod tidy`）与项目目录结构规范（`/cmd`、`/internal`、`/pkg` 的常见约定）

**动手练习**
1. 写一个并发抓取多个 URL 的小程序，用 `context.WithTimeout` 控制整体超时，超时后所有请求应该被取消。
2. 用 `go mod init` 建一个新项目，按 `/cmd/server`、`/internal/handler` 的结构组织代码（这个骨架会一直用到 Day 10）。

**参考资料**
- [A Tour of Go](https://go.dev/tour/)（如果并发部分不熟，重点过一遍）
- [Go 官方 Context 包文档](https://pkg.go.dev/context)
- [Standard Go Project Layout](https://github.com/golang-standards/project-layout)

**今日检查点**：能解释清楚"为什么 HTTP handler 里要把 `r.Context()` 一路传下去"。

## Day 2：构建生产级 HTTP 服务

**学习内容**
- 用标准库 `net/http` 写一个 RESTful 服务，再对比 [Gin](https://gin-gonic.com/) 框架带来的路由分组、中间件便利性
- 中间件模式：日志、恢复 panic、请求超时、CORS 是最常见的四类中间件，理解它们如何以"洋葱模型"包裹 handler
- 优雅关闭（Graceful Shutdown）：`http.Server.Shutdown()` + 监听 `SIGTERM` 信号——这一点在 Kubernetes 环境下**极其重要**，因为 Pod 被删除时 K8s 会先发 SIGTERM，服务必须处理完在途请求再退出
- 配置管理：环境变量优先（`os.Getenv`），或用 [Viper](https://github.com/spf13/viper) 统一管理配置文件 + 环境变量 + 命令行参数

**动手练习**
1. 用 Gin 写一个带有 `/health`、`/api/v1/items`（简单的增删改查，数据存内存 map 即可）的服务。
2. 实现优雅关闭：程序收到 `SIGTERM` 后，先停止接收新请求，等待现有请求处理完（最多等 5 秒），再退出。用 `kill -TERM <pid>` 手动测试。

**参考资料**
- [Gin 官方文档](https://gin-gonic.com/docs/)
- [Go 官方 Graceful Shutdown 示例](https://pkg.go.dev/net/http#Server.Shutdown)

**今日检查点**：手动发信号给进程，观察它是否真的等在途请求完成后才退出。

## Day 3：测试、日志与配置管理

**学习内容**
- Go 内置测试框架：`go test`、table-driven tests 写法、`httptest` 包测试 HTTP handler
- 结构化日志：为什么云原生场景要用结构化日志（JSON 格式）而不是 `fmt.Println`——因为日志最终会被 Loki/ELK 这类系统采集解析，结构化字段能被搜索和聚合。推荐 [zap](https://github.com/uber-go/zap) 或标准库 1.21+ 自带的 `log/slog`
- 分层配置：区分"编译期常量"、"环境变量"、"运行时可变配置"，理解 12-Factor App 原则中"配置存于环境"这一条为什么对容器化部署至关重要

**动手练习**
1. 给 Day 2 的服务补充单元测试，覆盖至少 2 个 handler，用 `httptest.NewRecorder()` 验证状态码和响应体。
2. 把所有 `fmt.Println` 替换成 `slog`，输出 JSON 格式日志，每条日志带上 `request_id`。

**参考资料**
- [The Twelve-Factor App](https://12factor.net/zh_cn/)（中文版，云原生的"圣经"，建议通读一遍，不长）
- [Go 1.21 slog 包文档](https://pkg.go.dev/log/slog)

**今日检查点**：`go test ./...` 全绿，日志能被 `jq` 直接解析。

## Day 4：Docker 基础与容器化你的服务

进入云原生的第一道真正的门槛：容器。

**学习内容**
- 容器 vs 虚拟机的本质区别（共享宿主机内核 vs 完整硬件虚拟化）
- Dockerfile 核心指令：`FROM`、`COPY`、`RUN`、`CMD`/`ENTRYPOINT`、`EXPOSE`
- **多阶段构建（multi-stage build）**：这是 Go 容器化的标准做法——第一阶段用完整的 `golang` 镜像编译出二进制文件，第二阶段用 `scratch` 或 `alpine` 这种极简镜像只装二进制，最终镜像能做到几 MB 到几十 MB
- 镜像层缓存机制：为什么 `COPY go.mod go.sum` 要写在 `COPY . .` 之前（利用 Docker 层缓存加速重复构建）

**动手练习**
1. 给 Day 3 的服务写一个多阶段 Dockerfile：

```dockerfile
# 构建阶段
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server ./cmd/server

# 运行阶段
FROM alpine:3.19
RUN apk --no-cache add ca-certificates
WORKDIR /root/
COPY --from=builder /app/server .
EXPOSE 8080
ENTRYPOINT ["./server"]
```

2. `docker build -t my-go-service:v1 .`，然后 `docker run -p 8080:8080 my-go-service:v1` 跑起来，用 `docker images` 对比镜像体积和用 `golang` 单阶段构建的差异。

**参考资料**
- [Docker 官方 Go 语言最佳实践](https://docs.docker.com/language/golang/)
- [Docker 多阶段构建官方文档](https://docs.docker.com/build/building/multi-stage/)

**今日检查点**：最终镜像体积应该在 20MB 以内（而不是几百 MB）。

## Day 5：Docker Compose 多容器编排

真实服务很少是孤立的——通常要连数据库、缓存。Compose 是学习"多容器协作"最平滑的起点。

**学习内容**
- `docker-compose.yml` 基本结构：`services`、`ports`、`environment`、`depends_on`、`volumes`
- 容器间网络：Compose 自动创建的网络里，服务之间可以用**服务名**互相访问（不是 `localhost`），理解这一点是后面理解 K8s Service 的基础
- 数据持久化：`volumes` 挂载，避免容器重启后数据库数据丢失

**动手练习**
1. 写一个 `docker-compose.yml`，同时启动你的 Go 服务和一个 PostgreSQL（或 Redis）容器，把内存 map 存储改成真正读写数据库。
2. 用 `docker-compose up`、`docker-compose logs -f`、`docker-compose down` 走一遍完整生命周期。

```yaml
services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      - DB_HOST=db
    depends_on:
      - db
  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_PASSWORD=example
    volumes:
      - db-data:/var/lib/postgresql/data
volumes:
  db-data:
```

**参考资料**
- [Docker Compose 官方文档](https://docs.docker.com/compose/)

**今日检查点**：能说清楚"为什么 Go 服务里连数据库要用 `DB_HOST=db` 而不是 `localhost`"。

## Day 6：Kubernetes 核心概念

正式进入云原生的核心——K8s。今天只建模型，不追求全会命令。

**学习内容**
- 为什么需要 K8s：Compose 只能管一台机器，K8s 解决的是"一堆容器分布在一堆机器上，自动调度、自动重启、自动扩缩容"的问题
- 五个必须理解的核心对象：
  - **Pod**：K8s 最小调度单元（通常一个 Pod 一个容器）
  - **Deployment**：声明"我要几个副本、用什么镜像"，K8s 负责维持这个状态、滚动更新
  - **Service**：给一组 Pod 提供稳定的访问入口（Pod 会被销毁重建，IP 会变，Service 不会）
  - **ConfigMap / Secret**：把配置和密钥从镜像里剥离出来，呼应 Day 3 学的"配置存于环境"
  - **Namespace**：逻辑隔离不同项目/环境
- 声明式 vs 命令式：K8s 的核心哲学是你描述"期望状态"（YAML），控制器负责让集群实际状态趋近期望状态

**动手练习**
1. `kind create cluster` 建一个本地集群。
2. `kubectl explain pod`、`kubectl explain deployment`，用官方内置文档过一遍字段含义（比死记 YAML 语法有效得多）。

**参考资料**
- [Kubernetes 官方文档 - Concepts](https://kubernetes.io/zh-cn/docs/concepts/)（有中文版）
- [Kubernetes 官方交互式教程](https://kubernetes.io/zh-cn/docs/tutorials/kubernetes-basics/)

**今日检查点**：能用自己的话说清楚 Pod、Deployment、Service 三者的关系，不用看文档。

## Day 7：把服务部署到 Kubernetes

**学习内容**
- 写 Deployment + Service 的 YAML，把 Day 4 构建的镜像部署上去
- **存活探针（liveness probe）和就绪探针（readiness probe）**：K8s 靠这两个探针判断容器是否健康、是否可以接收流量——这也是为什么 Day 2 要实现 `/health` 接口
- 资源请求与限制（`resources.requests` / `resources.limits`）：告诉调度器这个 Pod 大概需要多少 CPU/内存，避免一个服务把整个节点吃满
- 常用排错命令：`kubectl get pods`、`kubectl describe pod`、`kubectl logs`、`kubectl exec -it`

**动手练习**
1. 把镜像 `load` 进 kind 集群（`kind load docker-image my-go-service:v1`），写 Deployment 和 Service 部署上去：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: go-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: go-service
  template:
    metadata:
      labels:
        app: go-service
    spec:
      containers:
        - name: go-service
          image: my-go-service:v1
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 3
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
          resources:
            requests:
              cpu: "100m"
              memory: "64Mi"
            limits:
              cpu: "500m"
              memory: "128Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: go-service
spec:
  selector:
    app: go-service
  ports:
    - port: 80
      targetPort: 8080
```

2. 故意改错镜像名或探针路径，用 `kubectl describe pod` 和 `kubectl logs` 定位问题——排错能力比"一次部署成功"更重要。
3. 用 `kubectl port-forward svc/go-service 8080:80` 从本地访问服务。

**参考资料**
- [Kubernetes Probe 配置官方文档](https://kubernetes.io/zh-cn/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

**今日检查点**：故意 kill 掉一个 Pod（`kubectl delete pod <name>`），观察 Deployment 是否自动拉起新的替代它。

## Day 8：可观测性——日志、指标、健康检查

服务上线之后，"看得见"比"跑起来"更重要。

**学习内容**
- 可观测性三支柱：日志（Logs）、指标（Metrics）、链路追踪（Traces），今天重点做前两个
- Prometheus 指标暴露：用 [prometheus/client_golang](https://github.com/prometheus/client_golang) 给服务加一个 `/metrics` 端点，暴露请求数、延迟分布这类核心指标
- 指标类型：Counter（只增不减，如请求总数）、Gauge（可增可减，如当前并发数）、Histogram（分布统计，如响应耗时）
- 结合 Day 3 的结构化日志，理解"指标用来发现问题、日志用来定位问题"这个互补关系

**动手练习**
1. 给服务加上 `/metrics` 端点，暴露一个 HTTP 请求耗时的 Histogram 指标。
2. 本地跑一个 Prometheus 容器（`docker run -p 9090:9090 prom/prometheus`），配置 `scrape_configs` 抓取你的服务，在 Prometheus UI 里查询刚才暴露的指标。

**参考资料**
- [Prometheus Go client 官方文档](https://prometheus.io/docs/guides/go-application/)
- [Prometheus 官方文档 - 指标类型](https://prometheus.io/docs/concepts/metric_types/)

**今日检查点**：在 Prometheus UI 里能查到你自己服务产生的真实指标数据。

## Day 9：CI/CD 自动化流水线

**学习内容**
- CI（持续集成）与 CD（持续部署）的区别：CI 关注"代码提交后自动测试、构建"，CD 关注"构建产物自动发布到环境"
- 用 [GitHub Actions](https://docs.github.com/zh/actions) 写一个流水线：代码 push → 跑测试 → 构建镜像 → 推送到镜像仓库（如 GitHub Container Registry / Docker Hub）
- 镜像 tag 策略：为什么生产环境不该用 `latest`，而应该用 git commit sha 或语义化版本号做 tag

**动手练习**
写一个 `.github/workflows/ci.yml`：

```yaml
name: CI
on:
  push:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.22'
      - run: go test ./...
      - name: Build and push image
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

跑通后，观察 GitHub Actions 的执行日志，理解每一步在做什么。

**参考资料**
- [GitHub Actions 官方文档](https://docs.github.com/zh/actions)
- [docker/build-push-action](https://github.com/docker/build-push-action)

**今日检查点**：push 一次代码，能在 GitHub Actions 页面看到测试和构建自动跑完，镜像出现在仓库里。

## Day 10：综合实战 + 进阶地图

**今日任务：把前 9 天的所有知识串成一条完整链路**

1. Go 服务（Day 1-3）→ 2. Docker 多阶段构建（Day 4）→ 3. 本地 Compose 联调数据库（Day 5）→ 4. 部署到 K8s（Day 6-7，包含探针和资源限制）→ 5. 接入 Prometheus 指标（Day 8）→ 6. GitHub Actions 自动构建推送镜像（Day 9）。

把这条链路走完整一遍，你就拥有了一个"五脏俱全"的云原生项目模板，未来可以直接复用这个骨架去做新项目。

**进阶方向地图**（10 天之后可以按需选择深入）：

| 方向 | 关键词 | 什么时候需要 |
|---|---|---|
| 包管理与部署简化 | Helm | 当 K8s YAML 文件多到难以维护时 |
| GitOps | ArgoCD / Flux | 当团队想让 Git 仓库成为集群状态的唯一真相来源时 |
| 服务网格 | Istio / Linkerd | 当微服务数量变多，需要统一的流量控制、mTLS、灰度发布 |
| 分布式追踪 | OpenTelemetry / Jaeger | 当一个请求跨多个服务，需要追踪完整调用链 |
| 弹性伸缩 | HPA（Horizontal Pod Autoscaler） | 当需要根据 CPU/自定义指标自动扩缩容 |
| 云厂商托管 K8s | EKS / GKE / ACK | 当要把本地学的东西搬到真实生产环境 |
| gRPC | Protocol Buffers | 当服务间通信要比 REST 更高效、需要强类型契约 |

**最后的建议**：这份指南带你走完了骨架，但云原生这个领域"填肉"的过程需要真实项目里踩坑才能真正吃透。建议接下来找一个自己感兴趣的小项目（哪怕是个人博客后端），完整走一遍上面的十步，比再看十篇教程更有效。

## 附录 B：常见坑

- **忘记 `CGO_ENABLED=0`**：如果用 `scratch`/`alpine` 作为运行阶段基础镜像，编译时不禁用 CGO 会导致二进制依赖动态链接库，容器里跑不起来。
- **探针路径写错但没报错**：K8s 不会主动告诉你"探针失败了"，Pod 会一直重启，一定要养成 `kubectl describe pod` 排错的习惯。
- **本地 `localhost` 思维定式**：容器/K8s 环境里，服务间访问永远用服务名（Compose）或 Service 名（K8s），不是 `localhost`。
- **镜像 tag 用 `latest`**：会导致"我明明部署了新版本，但 Pod 里跑的还是旧代码"这种诡异问题，务必用具体版本号或 commit sha。
- **没设资源 limits**：一个内存泄漏的 Pod 在没有 limits 的情况下可能拖垮整个节点，压力测试前一定要先加上。
